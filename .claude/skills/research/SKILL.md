# Research Sessions

A **research notebook** is a directory whose immediate children are dated session
directories, plus a generated `INDEX.md`:

```
<notebook-root>/
  2026-08-06-laravel-turbopuffer/
  2026-07-14-sqlite-wal-behaviour/
  INDEX.md
```

Every investigation lives in exactly one such directory, named on the day the session
starts. This skill creates them, continues them, and answers questions across them.

Four things happen here. Pick one before doing anything else.

| Intent | Mode |
|---|---|
| A subject not yet researched | **New session** |
| More work on a subject already covered | **Continue** |
| A question spanning what's already been found | **Enquire** |
| "What have I researched?" | **List** |

Ambiguous asks default to checking existing sessions first — a duplicate directory on
the same subject is the one failure mode that degrades a notebook over time.

---

## Step 0 — main session only; refuse to run as a subagent

**If you are a subagent, stop here.** Report what you were asked to find out and let the
main session run this skill.

The frontmatter carries `disable-model-invocation: true`, so the harness admits only a
typed `/research`. Treat this step as the backstop for setups where that field isn't
honoured, and don't route around it by dispatching a subagent to run the skill for you.
Reaching for it unprompted is out of bounds even when a question obviously wants
research behind it — answer the question, and say that `/research` would capture it
properly.

**This does not forbid subagents inside a session.** Once the user has invoked the
skill, dispatching `Explore` or `general-purpose` agents to read widely, sweep sources,
or search a codebase is exactly the right move — they gather, you decide. What a
subagent must never do is *own the session*: choosing the mode, naming or creating the
session directory, writing `findings.md` / `sources.md` / `README.md`, or regenerating
`INDEX.md`. Those stay with the main session, which is the only place the user can be
asked about an overlapping subject or an unresolvable root.

## Step 1 — Resolve the notebook root

This skill is installed centrally and runs from whatever directory the session happens
to be in, which is usually **not** the notebook. Resolve the root before any mode does
anything, and say which root you resolved in your first reply:

1. **An explicit path in the ask** — `/research --root ~/notes/research`, or a path the
   user names in prose. Always wins.
2. **`$RESEARCH_NOTEBOOK`** if set and it exists.
3. **The current directory**, if it already looks like a notebook: it has an `INDEX.md`
   generated by this skill, or at least one `YYYY-MM-DD-*` child directory.
4. **A notebook folder inside the current project** — `research/`, `docs/research/`, or
   `.research/`, on the same test as (3). Projects that keep their research beside the
   code work this way, and the root is that folder, not the repo root.
5. **Ask.** Name the candidates you considered and let the user choose or supply a path.

**Never invent a root.** Scaffolding `2026-08-14-…/` into the top of somebody's
application repo because it was the working directory is the failure this step exists
to prevent — dated directories are conspicuous, and unpicking them is annoying. When
nothing resolves, ask; when the answer is "make one here", create the notebook
directory (with its `INDEX.md` header) as a deliberate, stated act.

Once resolved, offer to make it durable so the question isn't re-asked every session:
`RESEARCH_NOTEBOOK` in the settings `env` block for a personal notebook, or a line in
the project's `CLAUDE.md` for a project-local one. Offer — don't write it unasked.

Every path in the modes below is **relative to the resolved root**, never to the
current directory.

## Mode: New session

**1. Check it's actually new.** List the root's session directories and read the
`topic`, `slug` and `tags` front-matter of any that look adjacent:

```bash
grep -h '^topic:\|^tags:' <root>/*/README.md
```

If something plausibly overlaps, stop and ask whether to continue that session or start
a fresh one — that call is the user's, not yours.

**2. Name the directory.** `YYYY-MM-DD-subject-slug`, where the date is today
(`date +%F`) and the slug is 2–4 lowercase hyphenated words naming the *subject*, not
the question. `idiomatic-laravel`, not `how-should-i-write-laravel`.

**3. Scaffold it** from `templates/` in this skill directory (resolve them relative to
this `SKILL.md`, wherever it is installed):

```
<root>/YYYY-MM-DD-subject-slug/
  README.md      # front-matter, framing question, summary, open threads, session log
  findings.md    # the substance — what was actually learned
  sources.md     # every source consulted, annotated
  artifacts/     # code samples, downloads, diagrams, data, HTML pages
```

Write `README.md` front-matter first, before researching, so an interrupted session
still leaves a legible stub.

**4. Research.** Use `WebSearch` and `WebFetch`; fall back to the `playwright-fetch`
skill when a site blocks fetching, and say so plainly if that skill isn't installed and
a source stayed unreachable. Read code directly when the question is about a codebase.
Save anything downloaded, quoted at length, or worth re-reading into `artifacts/`
rather than leaving it only in the conversation.

**5. Write it up** as you go, not at the end:

- `findings.md` — claims with evidence, each traceable to a source. Record what was
  *ruled out* and why; that is the part you cannot reconstruct later.
- `sources.md` — one entry per source: URL, what it is, date accessed, and a line on
  whether it was useful. Mark anything authoritative (official docs, source code,
  spec) distinctly from anything opinionated (blog posts, forum threads).
- `README.md` — the framing question, a summary that stands alone, and open threads.

**6. Update `INDEX.md`** at the notebook root (see *Maintaining the index*).

Report: the directory created, the answer in a few lines, and any open thread worth a
follow-up session.

## Mode: Continue

Triggered by "add to the research", "follow up on X", or a subject that resolves to an
existing directory.

1. Resolve the target. Match against the slug, then `topic`/`tags` front-matter. On
   more than one plausible match, list the candidates and ask which.
2. Read that session's `README.md` and `findings.md` before adding anything — the point
   of continuing is not repeating.
3. Do the work; append to `findings.md` and `sources.md` under a dated sub-heading
   (`## 2026-08-14 — <what this pass covered>`), and add new files under `artifacts/`.
4. Update the session `README.md`: bump `updated:`, revise the summary if the picture
   changed, resolve or add open threads, and add a `Session log` row.
5. Update `INDEX.md`.

**The directory name never changes.** It records when the enquiry started, not when it
was last touched — `updated:` carries that. Renaming breaks every link into it.

If the follow-up has genuinely drifted to a different subject, say so and offer a new
session that cross-links back via `related:` rather than stretching the old one.

---

## Mode: Enquire

Read-only across sessions. "What have I found about connection pooling?", "did I ever
look at X?", "what contradicts what?"

1. Read `<root>/INDEX.md` for the map.
2. Search the corpus: `grep -ril '<term>' --include='*.md' <root>` then read the hits in
   full — front-matter `tags` and `topic` lines are the fastest first pass.
3. Answer in conversation, citing `directory/file.md` for each claim so the user can
   open the source. Where two sessions disagree, say so plainly with both dates — a
   later session does not automatically win, but note which is more recent.
4. Write nothing unless asked. If enquiring turns into new research, switch modes and
   say which mode you switched to.

---

## Mode: List

List the root's session directories, then read each `README.md`'s front-matter. Present
a table: date, topic, status, last updated, one-line summary. Flag sessions
`status: active` with no update in over a month as worth closing or reviving.

---

## Maintaining the index

`INDEX.md` at the notebook root is generated, not hand-curated. Regenerate it after any
session write, passing the resolved root as the argument:

```bash
bash <this-skill-dir>/scripts/index-rows.sh <root>
```

It is read-only — it prints one markdown table row per session, newest first, and
writes nothing. Put the output into `<root>/INDEX.md` with the Write tool, under this
header:

```markdown
# Research Index

Generated by the `research` skill. Do not hand-edit — it is overwritten.

| Date | Topic | Status | Updated | Tags | Directory |
|---|---|---|---|---|---|
```

If the script's output is missing a session, that session's front-matter is malformed —
fix the front-matter, don't patch the index.

## Rules

- **The user invokes this, never you.** Typed `/research` only — not on your own
  initiative, not from a subagent, not by dispatching one to run it. Subagents used
  *within* an invoked session are fine and encouraged.
- **Resolve the root first, and never guess it.** No session directory gets created in
  a repo that merely happened to be the working directory.
- **Everything lands in the session directory.** The only file written outside one is
  the notebook's `INDEX.md`. No stray notes at the notebook root, no scratch output
  that matters.
- **Front-matter is the query surface.** Every `README.md` carries the full schema in
  `templates/session-readme.md`. A missing `tags:` line makes a session invisible to
  future enquiry.
- **Cite or drop it.** A claim in `findings.md` with no source in `sources.md` is
  either marked `(inference)` or removed.
- **Uncertainty is content.** Record what remains unknown, what was contradictory, and
  what you could not access. Blank spots are findings.
- **Don't touch git.** Leave version control to the user — and don't assume the
  notebook is a repository at all; plenty are plain directories.
- **Prose over ceremony.** These are notes for a human to re-read in six months —
  write for that reader, not for a template.
